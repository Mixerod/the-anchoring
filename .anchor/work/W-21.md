## Why

W-20 made doctrine findable. It did not make doctrine affordable, and the second problem is
the one that decides whether a knowledge corpus can exist here at all.

Doctrine sits in **tier 1** of `kb brief` — the most stable, most expensive tier, whose whole
purpose is to be identical on every call so a prompt cache can match the prefix. Every byte
in it is paid by every agent on every cold start, whether or not the task has anything to do
with what the byte says.

Measured before this work:

```
$ wc -c .anchor/doctrine/*.md AGENTS.md
13887 total          # ~3,500 tokens, tier 1, every cold start
```

A corpus of engineering technique — the thing this repository is about to acquire — is on the
order of fifteen files. At the size a technique card needs to be useful, that is ~75 KB,
~19,000 tokens, added to tier 1 and paid forever. It would roughly double the whole brief to
deliver knowledge that any given task is ~95% likely not to need.

`src/config.ts` has been carrying the note that this was coming:

> a doctrine file may grow to any size, and every agent pays for it on every cold start,
> forever

So the corpus cannot be added until the cost model is fixed. Adding it first would be
shipping a regression and calling it a feature.

## What

A doctrine file declares where it lives:

```yaml
residency: brief   # full body in tier 1  (the default)
residency: index   # title + triggers in tier 1; body read on demand
```

This is the @skills protocol's tiering applied to prose, and deliberately so — the protocol
(`github.com/SylphAI-Inc/atskills`) exists because the same economics govern skills: a
reference costs nothing until used, and only auto-trigger residency is paid on every message.
`kb skills` already weighs that budget for skills. This weighs it for doctrine.

An `index` file still appears in tier 1 — as roughly fifty bytes of title, path, and
triggers, which is exactly the Tier-1 promise this repository already makes everywhere else:
enough metadata to decide what to read, without reading anything. `kb ask` and `kb ctx` then
name it when a trigger fires, and the agent reads one file instead of fifteen.

## Constraints honoured

- **`brief` is the default.** Every doctrine file that exists anywhere keeps its current
  behaviour with no edit. A cost mechanism that silently demoted existing documents would be
  changing what an agent reads without anyone deciding to.
- **The budget speaks.** `kb verify` warns, advisory and never gating, when tier-1 doctrine
  passes its budget. A budget nothing measures is a wish, and this specific hole has been
  documented in a comment for two layers without ever making a sound.

## Result

Indexing a 4 KB doctrine file costs **under 300 bytes** in tier 1 — measured by a test, not
asserted. Fifteen such files are ~4 KB resident instead of ~75 KB.

`kb verify` on the case that motivated this:

```
warn  15 resident doctrine file(s) · brief tier 1
      75000 bytes resident, 59000 over the 16000-byte budget; heaviest: ...
      -> every agent reads tier 1 on every cold start; add `residency: index` to the
         files a task rarely needs, so `kb ask` names them instead
```

## Note on three thresholds that came down

`config.ts` crossed its own 400-line limit and `parseConfig` was 244 lines against a 231
baseline. Neither number was raised.

- `src/config-schema.ts` was split out — the shape and its defaults change when the tool's
  opinion changes; the parser changes when the file format does. Two reasons to change, which
  is this repository's stated split rule and, until now, one it had not applied to itself.
- Leaving the types behind in `config.ts` made a cycle, and `depcruise` caught it on the
  first run. The types moved with the defaults that need them.
- `parseConfig` fell to 227 by giving both byte budgets one parser instead of two
  copies of twelve lines. The baseline came down to 227 to match.
